## Observations

- **Bug: a PDF with Han text cannot be exported on macOS 15.6 (EXP-30, and DEV-56's `scripts.lekh`).**
  Repro: Mac app, export-matrix (or any board with Chinese text in Noto Sans) → Export → PDF →
  Export. Expected (C++ / DEV-56, and as on web, iOS and Android): a PDF whose Han text is
  extractable, or at worst the text drawn as an image with the "Some text was exported as an image…"
  toast. Actual: "Error / An unexpected error occurred while exporting…" with no details and no
  file. The native `getFontData` for "中文…" (family Noto Sans) returns
  `tmp/fonts/PingFangSC-Regular.ttf` (54.6 MB, `variable: true`, `complete: true`, fsType 4). That
  face (PingFangSC-Medium in its name table) has `fvar`/`avar`/`HVAR` and Apple's new `hvgl`
  table but no `glyf`, `CFF ` or `CFF2` outlines. In Node with lekhjs's own fontkit, `getVariation`
  throws "Variations require a font with the fvar, gvar and glyf, or CFF2 tables" (caught in
  `openFont`), and then `font.layout(text)` throws `TypeError: Cannot read properties of null
(reading 'id')`. `layout` runs without a guard in `lekhjs/src/export/pdf/pdf-text-writer.ts:144`
  and `pdf-font-resolver.ts:158`, so the job ends in `export_internal`. The other fonts the Mac hands
  out (LucidaGrande for →, HiraginoSans-W3, AppleSDGothicNeo, GeezaPro, KohinoorDevanagari) open,
  lay out and embed fine. Suspected files: `lekhjs/src/export/pdf/font-embedding.ts` (`openFace` /
  `openFont` accept a face with no outline table; rejecting it would let the next source or the
  image fallback take over) and the unguarded `layout` calls above; and/or lekhios `getFontData`
  (FontUtil) handing out an `hvgl`-only face. iOS 16.7 passed because its PingFang has outlines.
- **Bug: a doc-list (folder) export hands off the partial file of a board that failed (EXP-36).**
  `lekhboard-capacitor/lekh/src/board/export/docListExport.ts` (~l.177-181): on `r.status ===
'failed'` the loop counts the error and continues, but the board's files already written to the
  shared delivery sink stay in it, so `handOff` passes a truncated PDF (1023 bytes here) next to
  the good one, then the summary alert says some boards failed. Expected: the failed board's
  files are dropped (as `exportRunner` discards a failed board-panel job), only the good ones are
  handed off, then "Error in exporting some of the boards.". Seen on the Mac because of the bug
  above; any board that fails mid-render would do the same on every native host.
- **The free-cap count happens when the picker closes (as on iOS, deliver.ts `handOff`).** On the
  Mac the picker is a sheet on the app's window, so Save, Move or Cancel always resolve it and the
  count went 1 → 2 on Cancel (EXP-33). Only quitting the app with the sheet up would skip it.
- With a native alert up (here the "Export Limitations" notice 800 ms after a board opened while
  capped, reached only because the harness started an export under it), the export's picker was
  not presented and the modal stayed at "Saving…"; its Cancel did not close it, and the app had to
  be relaunched. A user cannot press Export under a native alert, so this is not counted as a
  failure.
- The toasts of EXP-26/27 show right after Save / Move: on the Mac `shareFiles` resolves when the
  sheet closes.
- Exports are quick: every board-panel case reached the sheet in 1-3 s, EXP-27's three 33 MP pages
  in about 2.4 s.
- One file → a Save sheet with the file name; several → an open-panel sheet with "Move N items"
  (`UIDocumentPickerViewController initForExportingURLs:`). A cancelled single-file job leaves its
  file in the app's `tmp/export/<job>/`; moved files leave the job directory empty.
- With ad-hoc signing the WebView session does not survive a WebView reload (no keychain, as noted
  for DEV-01): an artefact of the test build.
